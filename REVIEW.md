# Jaycast review

Reviewed at `f23dfb5`: Rust core (~25k lines) and Swift shell (~7k lines).
`cargo test` passes (355 passed, 10 ignored). `cargo clippy` gives one warning: a function with too many arguments.

## Overall

This is a well-built codebase. The split between the two halves is clear: the Rust core owns behaviour and state, and the Swift shell only draws UI and forwards intent. That split holds across the code. The `unsafe` blocks carry `SAFETY` comments that actually justify them, and the code is commented well throughout. Most of what follows is hardening, not bugs.

## Strengths

- **Event taps are done properly.** Each tap runs on its own thread with its own run loop and `USER_INTERACTIVE` QoS. The callbacks are wrapped in `catch_unwind` and pass the event through on a panic. Config reaches the hot path through a generation counter, so the callback doesn't lock on every event. The taps re-enable themselves after `TapDisabledByTimeout`/`UserInput` and reset stale state. Teardown goes stop → invalidate → free. (`core/src/input/tap.rs`)
- **The FFI threading is consistent.** Every Rust observer callback is bounced through `DispatchQueue.main.async` before `MainActor.assumeIsolated`, so `assumeIsolated` is always sound. Slow work, such as Spotlight file search, runs in `Task.detached` with debouncing and a generation guard.
- **Security is handled carefully.**
  - Shell placeholders go through POSIX single-quoting, and a test round-trips them through a real `/bin/sh`.
  - Template expansion is single-pass, so substituted text is never expanded again.
  - Clipboard history is stored owner-only (0700/0600) and honours the nspasteboard Concealed/Transient/AutoGenerated types.
  - Commands run in their own process group, with a timeout that kills the group and bounded, drained output.
- **Config writes are atomic** (write to a temp file, then rename). The SQLite store has a `user_version` for migrations.

## Issues and recommendations

### High

1. ✅ **Fixed in `ea540f9`.** The core now uses `parking_lot` locks, which can't be poisoned.

   **Mutex poisoning can take the app down.** There are about 128 `lock().unwrap()` calls in the core. If any thread panics while holding a lock, every later FFI call that touches that lock also panics. UniFFI turns those panics into a Swift-side crash. A single bug in a background thread (DDC worker, clipboard poll, app watcher) would then crash the whole app instead of disabling one feature. Fix one of two ways:
   - Switch to `parking_lot::Mutex`/`RwLock`, which have no poisoning.
   - Or add a small `trait LockExt { fn locked(&self) -> MutexGuard<T> }` that calls `unwrap_or_else(PoisonError::into_inner)`.

   The taps already protect their callbacks with `catch_unwind`. The API surface deserves the same resilience.

2. ✅ **Fixed in `298215c`.** The clipboard store now has a separate read-only connection, so lookups never wait on a write. On a closer look, the launcher path was already fine: it holds no lock across disk or network work, and emoji and colour search only touch small in-memory lists. The calls stay synchronous.

   **The search APIs run synchronously on the main thread.** `core.search` (`Palette.swift:557`), `clipboardItems` (`PaletteModes.swift:33`), emoji search and colour search are called inline on every keystroke. They are fast today, but:
   - `search` takes the `usage` mutex, which a background index rebuild or app-watcher update could hold.
   - `clipboard_items` hits SQLite through a mutex shared with the poller's `insert`.

   Under contention this blocks the UI thread. Two options:
   - Make sure no lock on these paths is ever held across I/O.
   - Or move these calls onto the same detached-task pattern that file search uses.

### Medium

3. ✅ **Fixed in `bf383a2`.** Changes apply immediately. The file is written once changes have settled for 500 ms, and again on quit.

   **Config writes happen on every UI change, under the config lock.** `MouseSettings.config.didSet` → `set_mouse_config` serialises and writes the whole TOML file while holding `Core.config`. Dragging a slider means one fsync'd write per tick. Debounce the save on the shell side, or have the core apply the change immediately and persist it later.
4. **The core overwrites manual edits to `~/.config/jaycast.toml`.** The file is presented as user-editable, but nothing watches it or reloads it after launch. The in-memory `Config` overwrites any hand edits the next time a setting changes in the UI. Either watch and reload the file, or check its mtime before saving.
5. **There are no Swift tests and no CI.** The Rust test suite is good, but the shell has no test target and the repo has no CI workflow (`.github/` is missing). Add a GitHub Actions job that runs `just test`, `cargo clippy -- -D warnings` and `just build` on a macOS runner. It would catch FFI/binding drift, which no test currently covers.
6. **The generated bindings are not checked in.** That is fine, but a stale `Generated/jaycast_core.swift` can mismatch `libjaycast_core.a` without anything noticing (uniffi's checksum only fires at runtime). Make sure `just build` always regenerates the bindings. It does today, so keep it that way and don't add a fast path that skips them.

### Low

7. **Truncated command output can end with a replacement character.** `runner::drain` truncates at a byte boundary and then calls `from_utf8_lossy`, so a multi-byte character split at 64 KiB shows as `�`. Trim back to a char boundary (`str::floor_char_boundary` once stable, or a manual walk back).
8. **There are hand-written FFI declarations** (`kill`, `pthread_set_qos_class_self_np`, `AXIsProcessTrusted`, MDQuery). They are correct, but `libc` (already a transitive dependency) provides `kill`/`SIGKILL`/`pid_t` and removes one class of signature mistakes.
9. **`Core` is a 16-field god object** and `lib.rs` is a long flat FFI surface. It is fine at this size. If it grows, split it into per-feature `uniffi::Object`s (e.g. `core.clipboard().items(...)`) to keep the Swift API navigable.
10. **Some Swift files are large.** `Palette.swift` (1.4k lines) and `PaletteModes.swift` (800 lines) would read better split per mode (one file per mode model and view).
11. **Clippy flags `too_many_arguments` on `rank`.** Group its inputs into a `RankContext` struct.

## Verdict

Solid, idiomatic Rust and modern Swift 6 concurrency, and the hard parts (event taps, FFI threading, shell escaping) are handled carefully. Fix the poisoning cascade (#1) and the main-thread lock exposure (#2) first. Add CI before the codebase grows further.
